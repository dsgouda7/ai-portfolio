# Pre-Capstone Readiness Checklist

Use this gate before starting the Riverside capstone. It checks whether you can assemble an evidence-disciplined package; it does not certify production execution or FDE role readiness.

## Route foundations

- [ ] I completed or challenged out the AI Engineer prerequisites with cited evidence and limitations.
- [ ] I can explain the FDE role boundary and name the outside authority for customer scope, data use, security, compliance, commercials, production exposure, incident communication, and handoff acceptance.
- [ ] I can distinguish `[Measured]`, `[Modeled]`, `[Customer-validated]`, `[External validation required]`, and `[Unknown]` without promoting one class into another.
- [ ] I can trace an acceptance criterion through architecture, data/control, evaluation, rollout, operations, recovery, and handoff ownership.

## Artifact readiness

- [ ] I have reviewed the purpose and exit gate for modules 01 through 08.
- [ ] I can produce a discovery register with at least 20 evidence-bearing facts, claims, conflicts, or unknowns without inventing a resolution.
- [ ] I can compare no-AI, deterministic, search, RAG, prompt, adaptation, workflow, single-agent, and multi-agent options using named criteria.
- [ ] I can separate data readiness from retrieval or answer quality.
- [ ] I can define fail-closed negative tests for tenant, role, region, purpose, title assignment, entitlement freshness, and deletion state.
- [ ] I can build low/expected/high and stress scenarios while keeping every output modeled until retained execution evidence exists.
- [ ] I can distinguish deployment rollback from compensation or reconciliation for a committed external action.
- [ ] I can draft a redacted incident update that separates facts, hypotheses, unknowns, impact, containment, and the next update time.
- [ ] I can map every recurring task, alert, and change decision to an owner, action, evidence location, escalation path, and revalidation trigger.

## Ambiguity and communication readiness

- [ ] I can summarize two conflicting stakeholder statements neutrally without choosing the convenient one.
- [ ] For every unresolved conflict, I can name the decision owner, required authority, evidence needed, needed-by gate, blocked exposure, and escalation path.
- [ ] I can explain a `HOLD`, `NARROW SCOPE`, or `DO NOT PROCEED` recommendation in customer language without hiding uncertainty.
- [ ] A peer or mentor has reviewed one discovery summary or decision explanation for leading questions, unsupported certainty, authority confusion, and clarity.

## Stop conditions

Do not start the capstone package yet if any of these are true:

- you plan to complete blank fields by inventing customer approval, measurements, prices, cloud behavior, or legal/security conclusions;
- you cannot preserve an unknown as an owned blocker;
- you treat source code, a planned test, or a template as passing evidence;
- you cannot explain why a more complex architecture is necessary after evaluating smaller options;
- you expect the capstone score to establish independent production-execution competence.

Record failed items in a study or mentorship plan, revisit the owning module, and request a focused review. Passing this checklist means you are ready to attempt the static capstone, not ready to operate a customer production system without supervision.
